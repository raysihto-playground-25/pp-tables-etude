# 認証・ユーザー管理方針の検討まとめ（AWS / Web / Google+LINE / メールログインなし）

## 背景・目的

このドキュメントは、以下の課題を解決するための前提となるアカウント管理方針を整理したアイデアメモである。

- **チャットをより活用してもらうための方策を考える**：ユーザーがチャット機能を積極的・継続的に使えるようにするための施策を検討する。
- **セキュリティーレベルを上げる提案**：認証・アカウント管理の仕組みを強化することで、サービス全体のセキュリティを高める。
- **他人に見られてはいけないような会話も抵抗なくする**：信頼できる認証基盤を整えることで、プライベートな会話をためらいなくできる環境を提供する。
- **サービスとしての非推奨も示さなくて良くなる**：安全で明確な認証方式を採用することで、利用方法に関する免責・非推奨注記を減らし、シンプルなサービス提供を目指す。

---

## 1. 前提（議論で確定した条件）

- 個人プロダクト、利用料金は無料。
- 想定規模は月間 1,000 ユーザー程度。
- クライアントは Web のみ（デスクトップ／モバイルの両対応）。モバイルアプリ（iOS/Android）および CLI は無し。
- 大量流入時はサービス停止してもよい（可用性より運用容易性を優先できる）。
- 認証方式は「どうするのがよいか」を検討対象とする。
- 重要な要求：
  - ユーザーがそのとき利用しやすい実行環境（端末やブラウザ）を自由に選べること。
  - ブラウザの変動（複数ブラウザ利用等）を想定すること。
  - 複数ソーシャルログインがある場合に「どのソーシャルアカウントで登録したか」を毎回考えさせないこと。
  - アカウント統合（リンク）フローも実装したい。

---

## 2. 最終有力方針案（現時点）

### 2.1 認証方式（ユーザー向け提供）

**Google + LINE のみ**を提供する（メールログインは提供しない）。
アカウント統合（リンク）フローを実装し、統合後はどちらでもサインインできる状態を目指す。

### 2.2 ログイン画面（UX）方針

- 「どの IdP を使ったか」をユーザーに思い出させないため、**プライマリー ID プロバイダーを1つ定める**。
- **サインアップ時・サインイン時ともに、まずプライマリー ID プロバイダーのみを提示**する。
- プライマリー ID プロバイダーを明確に許容できないユーザーのみ、**セカンダリー ID プロバイダーへ誘導**する。
- 例：大ボタンはプライマリー（例：Google）だけ、小さなリンクで「使えない場合はこちら（LINE）」に誘導。

---

## 3. この方針に至る経緯（考え方と採否理由）

### 3.1 メールログインの扱い

- 当初、メールログイン（メール+パスワード、またはメールOTP）も選択肢として議論。
- しかし、最有力候補は **Google+LINE（メールログインなし）** へ収束。
- ソーシャルアカウントの普及度を踏まえ、門戸を広げすぎる必要性が低いという判断。
- 無料プロダクトのため、認証方式の数を増やして運用面を広げるより、提供方式を絞る方が合理的。

---

### 3.2 複数ソーシャルログインの「どれで登録したか問題」

- IdP を単純に縦並びで提示する UI は、登録時に「そのときの気分で選ぶ」余地がある。
- その結果、次回サインイン時に「どれで登録したか分からない」という認知負荷が発生しやすい。
- この問題は UX 上の主要な懸念点として認識された。

---

### 3.3 「状況に応じて」誘導する案の検討と限界

検討したシグナル：

- **(A) 明示的な履歴**（前回成功した IdP など）
- **(B) 現在の実行環境ヒント**（端末・OS・ブラウザ等）
- **(C) ブラウザ側記憶**（cookie / localStorage 等）
- **(D) 市場統計ベースの既定値**

評価：

- (A) は有効な場合は強力だが、端末・ブラウザ変更時には無効になり得る。
- (C) もブラウザ変動で無効化される。
- (B)(D) は環境変化を拾うことで、過去の選択とズレた誤誘導になる可能性がある。

結論：

> ユーザーが実行環境を自由に選ぶ前提を強く置く場合、  
> **推定中心のアプローチは本質的な解決になりにくい**。

---

### 3.4 プライマリー ID プロバイダー戦略を採用する理由

推定に頼らずに認知負荷を下げるため、**UI の規範化（デフォルト1択）** を採用。

期待効果：

- サインイン時に思い出す必要がない。
- サインアップ時の「気分で選ぶ」分岐を抑制できる。
- 端末・ブラウザ変動に依存しにくい。

トレードオフ：

- プライマリーを使えない／使いたくないユーザーには追加操作が発生。
- ただし本サービスでは「明確に許容できないユーザーのみをセカンダリーへ誘導」する方針で許容。

---

## 4. Cognito の位置づけ（現時点の理解）

- Cognito は必須ではないが、複数 IdP（Google / LINE）を扱う場合に実装・運用・保守の負担を下げ得る。
- プライマリー ID プロバイダー戦略も、Cognito 利用下で実現可能性がある。

---

## 5. Cognito 利用時の実現方式（未回答・要検討）

※ここは方式比較の整理のみ。最終選定は未了。

### 方式1：アプリ側 UI 主導（IdP 指定リダイレクト）

**概要**

- ログイン画面は自前で実装。
- プライマリー／セカンダリーの表示制御はアプリ側で行う。
- Cognito の `/oauth2/authorize` に `identity_provider` を付与してリダイレクトし、IdP 選択画面をスキップする。

**期待される利点**

- プライマリーのみ提示という UX を最も直接的に実現できる。
- 画面文言・導線・誘導ロジックの自由度が高い。
- 将来のアカウント統合誘導との親和性が高い可能性。

**懸念・未整理点**

- 実装責務の分担（アプリ側 vs Cognito 側）の最適点。
- managed login を使う場合との運用差分。
- セキュリティ／保守面での実装負荷の最終評価。

**ステータス：未回答**

---

### 方式2：App Client 分離による managed login 制御

**概要**

- 同一 User Pool に対して App Client を複数作成。
  - Client A：プライマリー IdP のみ有効。
  - Client B：プライマリー + セカンダリー有効。
- 通常導線は Client A、代替導線は Client B に誘導。

**期待される利点**

- Cognito の managed login を維持したまま、「最初はプライマリーのみ表示」を実現できる可能性。
- UI の一部を Cognito に委譲できる。

**懸念・未整理点**

- UX の細かな制御自由度。
- App Client 増加に伴う運用複雑性。
- 方式1との実装・保守コスト比較。

**ステータス：未回答**
